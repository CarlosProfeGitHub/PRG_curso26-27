    7. Pruebas de programas

    Un programa no está terminado cuando compila. Está terminado cuando hace lo que debe en todos los casos, incluidos los que ni se te ocurren. Esta unidad le da la importancia que merece al criterio de evaluación f) Se han probado y depurado los programas.

    La diferencia entre depurar y probar

    • Probar es ejecutar el programa con unos datos para comprobar que funciona. Se hace desde fuera.
    • Depurar es encontrar la causa exacta de un fallo. Se hace desde dentro, con herramientas que te dejan ver el estado interno del programa.

    Muchos estudiantes usan las dos palabras como si fueran sinónimos. No lo son: puedes probar mucho y no llegar a depurar nunca si tu programa, por suerte, no falla.

    7.1. Los dos tipos de prueba

    Tipo Pregunta que responde Conoce el código
    Caja negra (black box) ¿El programa devuelve el resultado correcto? No
    Caja blanca (white box) ¿Se ha ejecutado todo el código? ¿Cada instrucción hace falta? Sí

    Un ejemplo rápido de cada una

    Caja negra. El enunciado dice "calcula el área de un triángulo". Introduzco base 4 y altura 6, y el programa debe dar 12. No me importa cómo lo ha calculado: si el resultado es 12, funciona.

    Caja blanca. Abro el código y veo que hay un if cuya rama nunca se ejecuta. Esa rama es código muerto: no hace falta probarla porque es imposible llegar a ella, pero sí hay que eliminarla.

    7.2. La tabla de decisión

    Para probar programas con condiciones, la herramienta más útil es la tabla de decisión: enumera las combinaciones posibles de las condiciones y el resultado esperado.

    El enunciado es: clasificar una edad como menor de edad, adulta o anciana.

    # Condición Edad esperada Clasificación esperada ¿Ejecuta?
    1 edad < 18 12 Menor de edad Sí
    2 edad >= 18 && edad <= 65 30 Adulto Sí
    3 edad > 65 70 Anciano Sí
    4 Límite inferior 18 Adulto Sí
    5 Límite superior 65 Adulto Sí
    6 Límite inferior + 1 17 Menor de edad Sí
    7 Límite superior + 1 66 Anciano Sí

    El error clásico: probar solo el centro

    Si solo pruebas con edad = 30, funcionas: el programa acierta. Pero si escribiste edad > 18 && edad < 65 en lugar de edad >= 18 && edad <= 65, la fila 4 y la 5 fallarán. Los límites son donde fallan los programas.

    7.3. Los casos límite

    Un caso límite es un valor que está justo en el borde de lo que el programa debe aceptar, y un caso por debajo o por encima.

    Para un programa que pide notas de 0 a 10:

    Tipo Valor ¿Debe aceptarlo?
    Por debajo del mínimo −1 No
    Límite inferior exacto 0 Sí
    Por encima del mínimo 1 Sí
    En el centro 5 Sí
    Por debajo del máximo 9 Sí
    Límite superior exacto 10 Sí
    Por encima del máximo 11 No

    Probar siempre un valor por encima y otro por debajo de cada límite

    Es el consejo que más errores de programación evita. La mayoría de los bugs están en las comparaciones: < en lugar de <=, <= 100 en lugar de < 100.

    7.4. La técnica de la caja de cristal

    Método práctico y muy útil: ejecutar el programa mentalmente paso a paso, como si ejecutaras cada instrucción en un papel. Es la base de las trazas.

    1. Escribe el valor de cada variable en una tabla.
    2. Advanza una instrucción cada vez y anota los cambios.
    3. Cuando encuentres un if, escribe el resultado de la condición (true / false).
    4. Cuando encuentres un bucle, indica en qué iteración estás y cuál es el valor del contador.
    5. Cuando el bucle termine, salta a la instrucción posterior al bucle.

    Ejemplo resuelto

    int suma = 0;
int contador = 0;

while (contador < 4) {
    suma = suma + contador;
    contador++;
}

System.out.println(suma);
    Iteración contador contador < 4 suma
    Inicio 0 true 0
    1.ª vuelta 0 true 0 + 0 = 0
    2.ª vuelta 1 true 0 + 1 = 1
    3.ª vuelta 2 true 1 + 2 = 3
    4.ª vuelta 3 true 3 + 3 = 6
    Salida 4 false 6

    Se imprime 6. Si en el papel te sale otra cosa, tienes un error de traza o de código.

    7.5. Cómo escribir un programa que se pueda probar

    Un programa bien diseñado se puede probar sin necesidad de herramientas. Tres hábitos que ayudan mucho:

    1. Separa la entrada, el procesamiento y la salida

    // 1. Entrada
Scanner teclado = new Scanner(System.in);
int num1 = teclado.nextInt();
int num2 = teclado.nextInt();

// 2. Procesamiento
int suma = num1 + num2;

// 3. Salida
System.out.println(suma);

teclado.close();

    Si el procesamiento es una línea aislada, puedes probarlo sin el teclado.

    2. Pon el dato "quemado" al principio, no en mitad del código

    int a = 7;        // ✅ Fácil de cambiar para probar
int b = 9;
int c = a + b;
System.out.println(c);

    System.out.println("Resultado: " + (a + b));   // ❌ Difícil de trazar

    3. Escribe el resultado esperado ANTES de ejecutar

    Si ejecutas primero y luego "miras" el resultado, tu cerebro busca una justificación de lo que has visto. Si escribes antes lo que debería salir, detectas los errores de verdad.

    7.6. Prueba con datos absurdos

    Un programa que funciona con datos correctos puede romperse con los que el usuario escriba de verdad.

    Tipo de prueba Qué simula
    Valor vacío El usuario pulsa Enter sin escribir nada.
    Valor no numérico Escribe letras donde se espera un número.
    Valor cero División por cero.
    Valor negativo Números donde no se esperan negativos.
    Valor muy grande 999999999999 desborda el int.
    Valor de borde Exactamente el mínimo o el máximo permitido.

    Programa que se rompe con un 0

    Scanner teclado = new Scanner(System.in);

int divisor = teclado.nextInt();
int resultado = 100 / divisor;     // 💥 si divisor es 0

System.out.println(resultado);

    Con divisor = 10 funciona. Con divisor = 0 el programa se rompe con un error en tiempo de ejecución (ArithmeticException: / by zero). La solución completa —el control de excepciones— se trabaja en UD07.

    Scanner teclado = new Scanner(System.in);

int divisor;
do {
    System.out.print("Introduce un divisor distinto de 0: ");
    divisor = teclado.nextInt();
} while (divisor == 0);

int resultado = 100 / divisor;
System.out.println(resultado);

    Este patrón (do…while con una condición de salida) es el que se usa para validar la entrada del usuario, y lo verás en muchas actividades de la unidad.
